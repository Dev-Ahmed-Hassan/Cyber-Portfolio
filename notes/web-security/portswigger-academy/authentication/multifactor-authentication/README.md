# Vulnerabilities in Multifactor Authentication

> **Topic:** Authentication vulnerabilities  
> **Focus:** 2FA/MFA weaknesses, password reset issues, remember-me cookies, and related authentication mechanisms

---

## 1. What 2FA Is Supposed to Do

Two-factor authentication, or 2FA, is based on combining two different types of authentication factors:

- **Something you know**, such as a password.
- **Something you have**, such as a temporary code from a device you possess.

The main idea is that even if an attacker gets the user's password, they should still need access to the second factor before they can log in.

Usually, this second factor is a temporary code generated by an app, a hardware token, or sent to the user through an out-of-band channel.

---

## 2. Maximizing the Benefits of 2FA

2FA is only really useful when the factors being authenticated are actually **different**.

For example, email-based OTP codes are weaker than dedicated authenticator apps or hardware tokens because they still depend on the user having access to their email account. If the attacker already knows or compromises the email credentials, then the email OTP becomes more like single-factor authentication with extra steps.

This is why proper 2FA should ideally use an **out-of-band device** or a separate authentication channel.

---

## 3. 2FA Is Only as Strong as Its Implementation

Like any other security mechanism, 2FA is only as strong as the way it is implemented.

If the implementation is flawed or contains logical mistakes, then the effectiveness of 2FA becomes limited. A website may appear to have strong authentication, but if the server-side logic is weak, an attacker may still be able to bypass it.

So the important point is this:

> 2FA itself is not automatically secure. The actual security depends on how correctly it is enforced.

---

## 4. 2FA Tokens

Modern high-security systems often use a dedicated device for token generation. Examples include:

- RSA tokens
- Hardware keypad/token devices
- Authenticator apps such as Google Authenticator

The strong point in these methods is that the token is generated on the device itself. This means the code does not need to be transferred over a network or sent through another channel like email or SMS.

In contrast, some systems send tokens to the user's personal mobile device through SMS. This can be risky because the code has to be transmitted, and that transfer can potentially be intercepted.

SMS-based authentication can also be vulnerable to attacks such as **SIM swapping**, where the attacker takes control of the victim's phone number and receives the authentication code.

---

## 5. Bypassing 2FA by Skipping the Second Step

Sometimes a website asks for the password first and then asks for the 2FA token on the next page.

At that stage, the user may already be partially authenticated. The website might have created a session or treated the user as logged in before the second step is fully completed.

This can create a bypass if the application does not properly check whether the 2FA step has been completed before loading protected pages.

A basic thing to test is whether the 2FA page can simply be skipped.

For example:

1. Log in with a valid username and password.
2. Reach the 2FA verification page.
3. Try directly visiting a protected page such as `/my-account`.
4. Check whether the application allows access without completing 2FA.

If the server does not enforce the second step, then the 2FA is only present visually, not logically.

---

## 6. Broken 2FA Logic

A secure website should always track on the server side which user is trying to log in.

The server should not blindly trust browser-controlled values like:

```text
user=username
```

or:

```text
verify=username
```

If the website depends on a user-controlled cookie to decide which account is being verified, then the 2FA flow can become vulnerable.

For example, an attacker might:

1. Log in using their own valid credentials.
2. Reach the 2FA verification page.
3. Change a cookie such as `verify=wiener` to `verify=carlos`.
4. Start brute-forcing the OTP for the victim's account.

The main issue is that the server is trusting the browser to say which user is being verified.

The server should instead match the 2FA verification attempt with the same user who successfully completed the password-based login step.

---

## 7. Another Example of Broken 2FA Logic

Another logical flaw can happen when the application uses a cookie like this:

```text
verify=username
```

to decide which user's 2FA code is being checked.

If the application does not match this value with the user who completed the first login step, then the attacker can abuse this behavior by changing the cookie to another username.

For example:

```text
verify=carlos
```

Now the application may generate or verify the 2FA code for Carlos instead of the attacker.

This can lead to brute-force attacks against the victim's 2FA code, especially if proper rate limiting is missing.

---

## 8. Brute-Force Protection in 2FA

Systems can try to protect 2FA codes by logging the user out after a number of failed attempts.

However, this protection can still be bypassed if the full multi-step process can be automated.

For example, an attacker might automate the process like this:

1. Submit the username and password.
2. Reach the 2FA page.
3. Submit a limited number of OTP guesses.
4. If logged out, repeat the login step.
5. Continue brute-forcing the OTP.

This means brute-force protection must be enforced properly across the entire login flow, not just on one page.

The server should track failed attempts, rate-limit them, and make sure that logging in again does not reset the protection in a way that can be abused.

# Vulnerabilities in Other Authentication Mechanisms

Authentication is not only about the main login form.

Websites often have other authentication-related features, such as:

- Password reset
- Password change
- Remember-me functionality
- Account recovery
- Email verification

Most of the time, developers focus on securing the main login form against well-known attacks, but they may forget that these other mechanisms can be just as dangerous.

An attacker can create their own account, study these features, and look for logic flaws in how they work.

---

## 9. Keeping Users Logged In

Many websites have a feature like:

```text
Remember me
```

or:

```text
Stay logged in
```

This allows the user to bypass the normal login process on future visits.

To do this, the website stores some persistent value in the browser, usually inside a cookie.

This can become dangerous if the cookie generation logic is predictable.

Examples of weak cookie construction include:

```text
username:timestamp
```

```text
username:password
```

```text
base64(username:password)
```

```text
username:md5(password)
```

If the attacker can understand or guess how the cookie is created, they may be able to forge a valid cookie for another user.

---

## 10. Weak Encoding, Encryption, and Hashing in Cookies

Some websites assume that if a cookie value looks unreadable, then it must be secure.

But this is not always true.

For example, **Base64 is not encryption**. It is only encoding. If a cookie is just Base64-encoded, the attacker can simply decode it and understand the original value.

Hashing can also be weak if it is done without salting.

For example, if the cookie contains something like:

```text
username:md5(password)
```

then the attacker can take a password wordlist, hash each candidate password, and compare it with the hash in the cookie.

If no salt is used, then common password hashes may already exist in public hash databases. In that case, cracking or identifying the password can be as simple as pasting the hash into a search engine or hash lookup site.

The important point is:

> Encoding is not encryption, and unsalted hashes are weak against guessing attacks.

---

## 11. Brute-Forcing Remember-Me Cookies

Login forms often have rate limits to prevent brute-force attacks.

But if the remember-me cookie can also be guessed, the same level of protection must be applied there too.

Otherwise, the attacker can bypass login rate limits by brute-forcing cookie values instead of submitting passwords through the login form.

This is dangerous because the application may not treat cookie guessing as a login attempt, even though the impact is the same.

---

## 12. Studying Cookie Construction

If an attacker can create their own account, they can inspect the remember-me cookie generated for their own user.

They can then try to understand the pattern.

For example:

1. Create or use a known account.
2. Log in with the remember-me option enabled.
3. Capture the cookie.
4. Decode or analyze the cookie value.
5. Check whether it contains predictable data.
6. Try to generate a similar cookie for another user.

If the attacker cannot create their own account, they might use another vulnerability such as XSS to steal a user's session or persistent cookie and then study how it was made.

For open-source projects, the cookie construction logic may already be documented or visible in the source code.

---

## 13. Chaining Vulnerabilities

Vulnerabilities can be chained together to increase impact.

A vulnerability that does not seem very severe by itself can become dangerous when combined with another issue.

For example, weaknesses in remember-me cookies can be chained with:

- XSS
- CSRF
- Weak password reset logic
- Missing brute-force protection
- Predictable token generation

This is why even small authentication issues should not be ignored. They may become part of a bigger attack path.

---

# Resetting Passwords

When a user forgets their password, the website has to use an alternative authentication method to reset it.

This makes password reset functionality very sensitive.

If the reset flow is weak, then an attacker may be able to take over accounts without knowing the original password.

---

## 14. Sending Passwords by Email

For secure data handling, the actual password should never be sent by email.

Instead, the system should send a short-lived OTP or reset link through a secure channel.

Email itself is not ideal for highly sensitive data because:

- Emails stay in the inbox for a long time.
- Emails may sync across multiple devices.
- Email accounts may be accessed from different networks.
- Email communication can be exposed to interception or account compromise.

So sending the actual password by email is a bad practice.

---

## 15. Resetting Passwords Using a URL

Many systems reset passwords using a URL.

For example, the user receives a link and visits a reset page.

This becomes insecure if the URL parameters are easy to guess, such as:

```text
/reset-password?user=username
```

If the reset URL directly identifies the user and does not contain a strong secret token, then an attacker may be able to tamper with the URL and reset another user's password.

Usually, this method is combined with email. The reset link is sent to the user's email account.

---

## 16. Better Password Reset URL Implementation

A better implementation is to use a high-entropy, hard-to-guess token.

Example:

```text
/reset-password?token=a0ba0d1cb3b63d13822572fcff1a241895d893f659164d4cc550b421ebdd48a8
```

The token should not reveal anything about the user it belongs to.

The mapping between the token and the user should exist only on the backend.

When the user visits the reset URL, the server should check:

1. Whether the token exists.
2. Which user the token belongs to.
3. Whether the token has expired.
4. Whether the token has already been used.

After the password is reset, the token should be destroyed immediately.

---

## 17. Broken Password Reset Logic

A common logic flaw happens when the server validates the token only when showing the reset form, but does not validate the token again when the new password is submitted.

Example attack flow:

1. The attacker requests a password reset for their own account.
2. The attacker receives a valid reset link:

```text
/reset-password?token=attacker-valid-token
```

3. The attacker opens the link.
4. The server checks the token and shows the reset form.
5. When the form is submitted, the server does not check the token again.
6. The attacker removes the token or changes another parameter, such as `username`.
7. The server resets the password for whichever user is submitted in the POST request.

The issue is that the application trusts the POST request too much.

The server should validate the reset token at every sensitive step, especially when the password is actually changed.

---

## 18. Password Reset Poisoning

Even if the token itself is strong and hard to guess, the way the token is delivered can still be flawed.

Password reset poisoning happens when the attacker can influence the reset URL that is generated and sent to the victim.

This can happen if the application builds the reset link using data from the request itself.

For example, a vulnerable application may generate a reset URL using the `Host` header:

```text
{Host Header}/reset-password?token=victim-token
```

instead of using a trusted hardcoded domain like:

```text
https://site.com/reset-password?token=victim-token
```

If the attacker can change the `Host` header, they may be able to make the victim receive a reset link pointing to the attacker's server.

Example attack flow:

1. The attacker sends a password reset request for the victim.
2. The attacker modifies the `Host` header to point to their own server.
3. The application generates the reset link using the attacker-controlled host.
4. The victim receives the poisoned reset link by email.
5. The victim clicks the link.
6. The request goes to the attacker's server, leaking the reset token in the URL.
7. The attacker checks their server logs and extracts the token.
8. The attacker uses the token on the real website to reset the victim's password.

The core issue is that the application trusts user-controlled input when generating sensitive password reset links.

---

## 19. Password Change Functionality

Password change pages can also be vulnerable.

Even though password reset is usually discussed more, password change functionality can also lead to account takeover if implemented badly.

For example, the password change page may be vulnerable if:

- It does not properly verify the current password.
- It leaks different responses for valid and invalid current passwords.
- It allows brute-forcing the current password.
- It trusts user-controlled parameters to decide which account's password is being changed.
- It lacks rate limiting.

Password change functionality should be protected just as strongly as the main login and password reset flows.

---

# Final Summary

2FA and other authentication mechanisms can add strong protection, but only when they are implemented correctly. A weak 2FA flow can be bypassed if the server does not properly track the login state or trusts browser-controlled values like cookies. Similarly, remember-me cookies, password reset links, and password change pages can all become account takeover paths if their logic is flawed.

The main lesson is that authentication security is not only about the login form. Every feature that proves identity, restores access, or keeps a user logged in must be treated as part of the authentication system and protected carefully.

---

# Key Lessons Learned

- 2FA is useful only when the two factors are truly different.
- Email-based OTP can be weaker because it still depends on email account security.
- The server must track which user is completing 2FA instead of trusting browser-controlled cookies.
- 2FA pages should not be skippable by directly visiting protected pages.
- Brute-force protection must apply across the whole authentication flow.
- Remember-me cookies are dangerous if their structure is predictable.
- Base64 is encoding, not encryption.
- Unsalted password hashes can often be cracked or looked up.
- Password reset tokens must be high-entropy, short-lived, single-use, and validated at every step.
- Password reset poisoning can happen when reset URLs are generated using attacker-controlled request data.
- Password change functionality should be tested and protected just like login and password reset flows.
- Small vulnerabilities can become serious when chained together.
